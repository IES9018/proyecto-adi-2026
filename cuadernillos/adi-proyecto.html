SPEC: el contrato del sistema

La SPEC describe propósito, alcance, requisitos funcionales numerados (RF-01, RF-02…), Non-Goals explícitos y contratos de datos. No es un documento de diseño: es contra lo que se mide si el código es correcto.

Non-Goals: lo que NO hace esta versión. Ej: “esta versión no maneja autenticación de usuarios”, “esta versión no genera reportes PDF”. Declararlos evita que la IA agregue funcionalidades no pedidas.

ADR-001: decisión de stack

Documentá la elección de tecnologías (lenguaje, framework, base de datos) con al menos dos alternativas descartadas. Cada alternativa debe tener criterios objetivos: curva de aprendizaje, ecosistema, compatibilidad con el proyecto.

OpenAPI: contrato primero

Los 5 endpoints críticos de tu SPEC se definen en OpenAPI 3.x antes de escribir código: path, método, parámetros, schemas request/response, códigos de error (400, 401, 404, 500 mínimo). El archivo debe pasar un linter (@redocly/cli lint).

VER CUADERNILLO 01 → OpenAPI

Autenticación insuficiente JWT con security scheme en OpenAPI
Exposición de datos sensibles Filtros de respuesta en endpoint

Pipeline CI

Workflow que se ejecuta en cada PR hacia main: 1. Lint del contrato: valida api-contracts.yaml con @redocly/cli lint 2. Tests: corre la suite unitaria (mínimo 5 tests) 3. Build: compila el proyecto

Agregá el badge de estado del CI al README. PR con CI rojo = merge prohibido.
